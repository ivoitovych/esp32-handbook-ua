# Фактчекінг, прохід 10: повідомлення в консолі

Дата: 2026-08-26. Звірено всі рядки, які книга обіцяє читачеві побачити
в логу, — не з документацією, а з самими рядками у вихідному коді, який
їх друкує.

**Шість виправлень.** Найбільше за всі десять проходів.

## Чому критерій тут суворіший

Довідник цього жанру каже: «побачиш такий рядок — роби те». Якщо рядок
надрукований неточно, читач шукає його у своєму логу дослівно, не
знаходить — і порада зникає разом із рядком. Тут має збігатися не зміст,
а **текст**.

Саме тому джерелом узято код, а не документацію: документація переказує
повідомлення, код їх друкує.

## Виправлення 1: `MD5 does not match` не існує

Книга друкувала цей рядок у **п'яти** місцях як типовий симптом просадки
живлення при прошивці.

Справжній текст esptool:

```python
raise FatalError("MD5 of file does not match data in flash!")
```

Підрядка `MD5 does not match` у ньому немає: між `MD5` і `does` стоїть
`of file`. Пошук у логу давав порожньо.

Виправлено на `MD5 of file does not match` в усіх п'яти місцях.

## Виправлення 2: тексти помилок esptool застаріли на дві версії

Книга наводила формулювання esptool 3.x.

| Книга друкувала | Насправді (v5) |
|---|---|
| `Timed out waiting for packet header` | `No serial data received.` |
| `This chip is X not Y` | `This chip is X, not Y. Wrong chip argument?` |
| `Stub is disabled` / `Failed to run stub` | `Failed to start stub flasher. There was no response.` |

Перший рядок — найчастіша помилка взагалі, і книга сама називає її
найчастішою.

Третій випадок цікавий окремо: рядка `Stub is disabled` немає зовсім, а
є попередження `Stub flasher has been disabled for compatibility, set
--no-stub to suppress this warning.` — і воно **не помилка**: esptool сам
вимкнув stub і працює далі. Книга подавала це як збій.

Порівняння з гілкою `v4.8.1` показало, що і в v4 тексти вже були інші
(`Failed to start stub.`, `Wrong --chip argument?`). Тож там, де
формулювання розійшлися помітно, тепер названо обидва — книга вже
розрізняє синтаксис v4 і v5 у командах, тепер розрізняє й у помилках.

## Виправлення 3: `Flash chip size mismatch` не існує

Рядка з такою назвою в ESP-IDF немає ніде. Справжніх рядків **два**, і
наслідки в них протилежні:

```c
ESP_EARLY_LOGE(TAG, "Detected size(%dk) smaller than the size in the binary
                     image header(%dk). Probe failed.", …);
ESP_EARLY_LOGW(TAG, "Detected size(%dk) larger than the size in the binary
                     image header(%dk). Using the size in the binary image header.", …);
```

Реальний флеш **менший** за налаштований — фатально, проба зупиняється.
**Більший** — лише попередження, система працює, надлишок не
використовується.

Друге — типова доля клонів, що продаються як 16 МБ і виявляються 4 МБ.
Книга подавала обидва випадки одним рядком і одним наслідком.

## Виправлення 4: `image has invalid SHA256` не існує

ESP-IDF друкує `Image hash failed - image is corrupt`.

Це рівно той випадок, заради якого прохід і робився: читач із
пошкодженим образом шукав у логу рядок, якого там ніколи не буде.

Заразом решту рядків таблиці бутлоадера доповнено до повного вигляду —
`image at 0x… has invalid magic byte (nothing flashed here?)`,
`ota data partition invalid, falling back to factory`, — бо саме хвіст
рядка каже, що бутлоадер зробив далі.

## Виправлення 5: обрізаний рядок Task WDT ховав головне

Книга друкувала:

```
E (5234) task_wdt: Task watchdog got triggered.
E (5234) task_wdt: - IDLE0 (CPU 0)
```

Насправді перший рядок довший:

```c
const char *caption = "Task watchdog got triggered. "
                      "The following tasks/users did not reset the watchdog in time:";
```

Обрізане саме те речення, яке пояснює різницю між двома переліками в
дампі:

- після першого рядка — ті, хто **не встиг погодувати** watchdog; у
  типовому випадку `IDLE0`, тобто потерпілий;
- після `Tasks currently running:` — те, що виконувалося в цю мить, і
  саме там винуватець.

Книга цю різницю знала й писала про неї прозою, але друкувала лог, з
якого її не видно. Тепер надруковано повний рядок, а тлумачення винесено
в блок уваги — у розділі 26 і додатку D.

Заразом виправлено відступ: формат `" - %s%s"` дає два пробіли після
двокрапки тега.

## Доповнення: `CORRUPT HEAP` розрізняє бік переповнення

Книга мала один рядок. Купа насправді каже, з якого боку писали повз:

```c
MULTI_HEAP_STDERR_PRINTF("CORRUPT HEAP: Bad head at %p. …");
MULTI_HEAP_STDERR_PRINTF("CORRUPT HEAP: Bad tail at %p. …");
```

`Bad tail` — за кінець блоку: класичне переповнення буфера, шукати
`memcpy`, `sprintf`, цикл із `<=` замість `<`.

`Bad head` — **перед** початком: від'ємний індекс, зсув покажчика назад.
Трапляється рідше й майже завжди означає помилку в арифметиці
покажчиків.

Це звужує пошук удвічі й не коштує нічого. Додано в додаток D разом із
поясненням, що адреса в рядку — адреса канарки, тобто край блоку.

Рядок про переповнення стека доповнено до повного:
`***ERROR*** A stack overflow in task X has been detected.`

## Що звірено без розбіжностей

**Формат паніки — точний, включно з тонкістю.** Книга друкує
`Guru Meditation Error: Core 0 panic'ed (LoadProhibited). Exception was
unhandled.` з реченням у кінці, а `… (Interrupt wdt timeout on CPU0)` —
без нього. Саме так поводиться код: для звичайних винятків
`description` виставлено, для псевдопричин він `NULL`.

Усі вісім назв винятків із таблиці додатка D є в масиві `reason`
дослівно. `Cache disabled but cached memory region accessed` — теж.

**Рядки бутлоадера** `Factory app partition is not bootable`,
`partition N invalid magic number`, `Failed to verify partition table` —
дослівні.

**`Camera probe failed`** — точний початок справжнього рядка
(`Camera probe failed with error 0x%x(%s)`), пошук спрацює.

**Boot-лог ROM** — підтверджено проходом 8 з документації esptool.
